# Agent Note：历史页按原始事件数封顶

Status: implemented

[English](2026-08-24-history-page-raw-event-bound.md) | 中文

## Problem

`session.history` 只按消息数分页：一页是覆盖最新 `maxMessages` 条追加来源消息（默认 50 条）的原始事件区间。页内的原始事件数没有上限，而逐字符增量输出的提供方——CJK 文本每个 chunk 只有一到两个字符——每条消息大约落一千个 chunk 事件。这类提供方上的长对话，一页 50 条消息可达 57,000+ 原始事件（12.5 MiB JSON）。Web 客户端同步吞下整页：`ConversationNodeAssembler.replaceWindow` 在主线程上对每个事件排序、索引并跑全部节点定义的匹配，再渲染。实测 57,000 事件的框架地板开销在 Node 中为 839 ms，浏览器里叠加真实定义与渲染还要放大数倍——对话区打开为空白，极端时渲染进程直接冻结。而会话数据在磁盘上始终完好，这让故障看起来像数据丢失。[2026-08-04-large-history-pagination-call-stack](2026-08-04-large-history-pagination-call-stack.zh.md) 修复了同一条回放路径上的服务端崩溃，并明确把页大小问题留作独立事项；本笔记补上它。

## Decision

`dsh-host-apiproxy` 的 `paginate` 额外用 `MAX_PAGE_EVENTS = 10_000` 原始事件为页封顶。从尾部向回走，当下一条消息组入页会越过上限时，切割点落在已接纳的最新一组起点——绝不切进组内。最尾部的那条消息总是被接纳，即使它单独一组就超限，因此页永不为空且每条消息都可达：被拒的组成为下一个 `beforeSeq` 页的唯一尾部消息。当剩余消息全部放得下时行为不变（cut 为 0、整窗口），消息数上限的既有语义逐字保留。上限检查通过在按 seq 升序的窗口上二分查找 `lowerBoundSeq` 完成，回走保持 O(消息数 · log 事件数)。

回归测试构造三条高密度消息——两条各 5,501 原始事件（合计 11,002，越过上限）、一条 10,501（单独越限）——验证得到的三页：前两页各携带恰好一个已接纳的组且 `hasMore` 为真，第三页整组落地且回走自然结束于 cut 0。并在触发故障的真实会话上验证：同一请求从 57,778 事件 / 12.5 MiB 降到 8,272 事件 / 1.8 MiB。

## Alternatives considered

- **让客户端增量或离开主线程吞页** —— 暂缓：`replaceWindow` 是与实时缝合共享的打开/重同步/断档修复路径，分块异步处理会改变所有消费方的发布语义；服务端封顶不动客户端就修复了每个客户端（Web、SDK、subagent history）的故障。
- **客户端调低 `PAGE_MESSAGES`** —— 否决：任何固定消息数都依赖提供方；chunk 更密的提供方会再次触发冻结。
- **从历史响应中裁掉 chunk 事件** —— 否决：客户端的部分消息装配要回放 chunk 事件；丢弃会破坏进行中的轮次以及一切按溯源重建消息的消费方。

## Consequences

- 每个历史页被 `max(上限, 最大单条消息组)` 原始事件约束，客户端的同步吞页成本与提供方 chunk 密度无关地有界。
- chunk 密集的对话每页消息更少（本例约 7 条），随用户上滚分页加载更早历史；稀疏提供方仍保留整 50 条消息的页。
- 线上契约不变（`maxMessages`/`beforeSeq`）；正确处理 `hasMore` 的客户端无需改动。
- 若将来页需要超出上限增长，客户端增量吞页仍是更深的修法。
