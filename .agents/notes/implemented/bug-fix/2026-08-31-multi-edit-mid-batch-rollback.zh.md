# Agent Note：multi_edit 在批量写入中途失败时回滚已写入文件

Status: implemented

[English](2026-08-31-multi-edit-mid-batch-rollback.md) | 中文

## 问题

`multi_edit` 的写入阶段是顺序且非事务的：前面的文件已落地后某次写入失败，会让这批编辑以半应用状态留在磁盘上，而抛出的报告只点名哪些文件已落地。调用方发起跨文件批量编辑，正是因为这些编辑彼此关联——部分落地是一个损坏的中间状态，调用方只能手工清理：重新读取每个已落地文件并恢复其先前内容。

## 决策

保留两阶段流程。批量写入中途失败时，工具现在会把每个已写入的文件恢复为批前内容，按写入的逆序进行：

- 计划阶段在每个文件的演进内容之外同时保留其原始内容。
- 写入阶段记录每次写入产出的版本（`FsWriteOutcome.version`）；每次恢复都是一次带版本守卫的 `replaceIfVersion` 全量写入，把原始内容写回该产出版本。若文件在批量写入与恢复之间又被改动，恢复会失败而不是覆盖。
- 抛出的失败信息点名打断批次的文件、统计已恢复的写入文件数；当恢复本身失败时，点名所有已编辑内容仍留在磁盘上的文件。第一个文件就失败时不执行任何恢复，报告中不出现回滚字样。

## 已考虑的替代方案

- **保留仅报告行为** —— 拒绝：部分批次留在磁盘上成为调用方的问题。
- **全部写入暂存区再换入** —— 拒绝：文件系统接缝的带版本守卫 `writeText` 已提供单文件原子性；暂存协议会在该保证之后复制出第二种失败模式。
- **用 `editText` 反向编辑恢复** —— 拒绝：批前内容已在内存中，带守卫的全量写入更简单且不会遗漏。

## 后果

- 失败的批次会把工作区恢复为调用前的状态，恢复本身失败时除外；该情况响亮报错并点名未恢复的文件。
- 恢复写入有意不携带调用自身的执行信号：它们是对本次调用部分写入的有界清理，即使调用正在被取消也必须完成。
- 失败路径上每个已写入文件至多多花一次写入。成功路径不变。
