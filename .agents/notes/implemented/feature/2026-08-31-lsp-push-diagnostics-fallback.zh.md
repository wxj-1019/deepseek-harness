# Agent Note：推送诊断回补拉取失败而不是直接报错

Status: implemented

[English](2026-08-31-lsp-push-diagnostics-fallback.md) | 中文

## 问题

服务器到客户端的通知在连接解码循环中被直接丢弃，而对不支持拉取式诊断的服务器发起 `diagnostics` 查询会 outright 失败——尽管这类服务器大多会在文档打开的瞬间推送 `publishDiagnostics`，而瞬态打开生命周期本来就已在每次查询时触发了这一时机。

## 决策

- `LspConnection` 新增 `onNotification` 注册表；解码循环把每条通知扇出给监听者，每次调用相互隔离，抛错的监听者无法杀死帧流。
- `LspInstance` 订阅 `textDocument/publishDiagnostics`，归一化每次推送（`normalizePublishDiagnostics`；畸形推送作为服务器噪音丢弃，绝不变成查询失败），并按文档 URI 缓存最新集合，达到 32 个文档时按最旧条目淘汰。
- 对不支持拉取的服务器发起 `diagnostics` 查询不再失败：瞬态打开照常执行，查询在有界的 `publishGraceMs`（服务器配置，默认 250 ms）内等待一条比查询开始更新的推送并返回之；宽限静默到期则返回空集。拉取路径的查询不受影响；等待只随调用者的中止信号，宽限到期通过循环内的缓存检查退出，而不是以拒绝的形式。

## 已考虑的替代方案

- **保持文档持续打开以连续接收推送** —— 拒绝：那会放弃保持零文档状态的瞬态打开生命周期并使池化复杂化；有界等待在既有窗口内获得了同样的新鲜度。
- **无拉取支持时响亮失败（原行为）** —— 拒绝：它让所有仅推送的服务器对工具毫无用处，尽管推送通道携带同样的数据。
- **把推送作为主动事件暴露给模型** —— 拒绝：模型可见输入必须是被请求的；工具拥有的查询仍是唯一的诊断表面。

## 后果

- 仅推送的服务器现在能应答 `lsp` 诊断查询；代价是在不支持拉取的服务器上每次查询至多一个有界宽限。
- 缓存至多持有 32 个文档；畸形推送从不使查询失败。
- `publishGraceMs` 加入逐服务器校验配置；支持拉取的服务器不会增加任何延迟。
