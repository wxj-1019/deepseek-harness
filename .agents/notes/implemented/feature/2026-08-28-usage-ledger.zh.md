# Agent Note: 用量台账与“用量”设置分区

Status: implemented

[English](2026-08-28-usage-ledger.md) | 中文

## 问题

token 计量此前只对当前打开的会话可见：`tokenUsage` 会话投影（token-meter）与输入框统计行描述的都是当前会话，其余表面全盲。管理多个会话的用户得不到跨会话的“我花了多少 token、花在哪”的答案——而回答它的数据（`assistant/message` 事件上 provider 上报的用量）本来就在会话事件流里流动，只是没人收集。

## 决策

新宿主包 `@deepseek-ai/dsh-usage-ledger` 拥有一个 `usage_ledger` 存储域：每会话一行，累积 provider 四桶（输入、输出、缓存读、缓存写）、样本数与最新样本的墙钟时间。采集器在 init 时订阅 `session/event`，把每条带用量的 `assistant/message` 样本累加进去；同会话样本经每会话写链串行化，`list()` 等待在途链，读取绝不漏掉刚落地的样本。每次累加发出白名单事件 `usage-ledger/changed`。

客户端包 `@deepseek-ai/dsh-client-ui-usage` 渲染“用量 / Usage”设置分区：每会话一行展示四桶、行合计与最近活跃时间；合计行对可见行求和；会话标题经标准 sessions kit 解析。分区挂载即加载；推送与断线重连让已加载的表格收敛。

台账只观察用量、绝不产生用量：这里没有任何内容模型可见，投影词汇也不新增成员（既有的 `tokenUsage` 单元继续服务输入框的当前会话）。

无 key 的 web 旅程 `apps/web/tests/usage-dashboard.e2e.ts` 只读复用通知中心的回合夹具：回放落定成为台账一行，分区展示该会话的行与非零合计，合计行把它求和。单元套件钉住累积、排序、无用量消息不计数与重启持久（`packages/session/usage-ledger/tests/usage-ledger.spec.ts`）。无 key 旅程只读复用通知中心的回合夹具，因此无需新的录制。

## 考虑过的替代方案

- **渲染时从 session-query sqlite 聚合。** 未采纳：sqlite 索引是可选项且默认关闭，为仪表盘塑形一个查询后端不如在事发当下写入的存储域——更简单且常开。
- **给 token-meter 加跨会话折叠。** 未采纳：token-meter 刻意每会话一份独立折叠；跨会话表是不同的归属，不是更多折叠。
- **用会话投影而非存储域。** 未采纳：用量合计是跨会话用户状态——storage domain 的范式场景。
- **v0 就带重置/保留动词。** 推迟：重置不触碰任何其他面，随时可加；不带它发布使写面保持读形状。

## 后果

- “用量”分区回答自台账挂载以来跑过的每个会话“花了多少”，且对其后运行的内容实时更新。
- 各桶数字是 provider 上报的精确值；台账不含任何启发式估计（不同于 token-meter 的表面估计）。
- 行不随会话死亡——删除级联（被延后的原语）落地时需要与反馈、置顶边车同样的清扫。
- 面板表格的规模以会话数为界；按模型或按天切分需要台账 schema 升版本。

## 风险

- **替换样本理论上重复计数。** token-meter 的排序性质保证合法日志安全；限制已记录。
- **跨窗口分区陈旧。** 没有白名单推送时第二个窗口的分区会陈旧；推送加重拉已接线并被覆盖。
- **冷启动可见性。** 分区挂载即加载，首次打开付出一次 list 读取——以会话数为界。
